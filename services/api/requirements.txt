# Web framework (Flask monolith + thin FastAPI mount for device-management)
# Flask 3 stack. These five move together or not at all: Flask-JWT-Extended
# 4.5.3 and Flask-Limiter 3.5.0 were both pinned against Flask 2.x, so bumping
# Flask alone leaves an unsatisfiable set. Versions below are what pip itself
# resolves for Flask>=3.1.3 + Werkzeug>=3.1.6 + Flask-Cors>=6.0.0, not a guess.
Flask==3.1.3
# Werkzeug still pinned explicitly rather than floating: Flask's own constraint
# is a lower bound, and Werkzeug majors have removed APIs before (which is why
# 2.3.8 was pinned here in the first place).
Werkzeug==3.1.9
Flask-Cors==6.0.5
Flask-JWT-Extended==4.7.4
Flask-Limiter==4.1.1
simple-websocket==1.0.0
gunicorn==23.0.0

# FastAPI sub-application (telemetry/dashboard module) mounted via a2wsgi
# fastapi 0.100.1 carried PYSEC-2024-38, and its Starlette (0.27.0) seven
# advisories, the last fixed only in Starlette 1.3.1 (PYSEC-2026-249). FastAPI
# 0.133.0 is the first release that supports Starlette 1.x. Starlette is pinned
# here, not left to FastAPI's open lower bound, so the image cannot fall back
# to a vulnerable release. Every FastAPI >= 0.126 requires pydantic 2; see the
# pydantic pin below.
fastapi==0.133.0
starlette==1.3.1
a2wsgi==1.10.4

# Datastores
# pymongo 4.18.3 is the lowest release that clears PYSEC-2026-4294..4297 and
# CVE-2026-106435. motor moves with it: motor 3.4-3.5 import pymongo internals
# that were removed in pymongo 4.9, and motor 3.6 caps pymongo below 4.10, so
# 3.7.0 is the lowest motor that runs on this pymongo.
pymongo==4.18.3
motor==3.7.0
psycopg2-binary==2.9.7
redis==4.6.0

# HashiCorp Vault PKI client (certificate lifecycle)
hvac==1.1.1

# Auth + crypto (JWT, bcrypt, x509)
# 2.13.0 clears six advisories, including CVE-2026-32597: PyJWT accepted unknown `crit` header
# extensions, contrary to RFC 7515. This service signs and verifies its own
# HS256 tokens with its own JWT_SECRET (api/core/auth.py), so the practical
# exposure is low — but it is a small, same-major bump, so there is no reason
# to carry the finding.
#
# 2.15.0 is the lowest release that clears the 2026 batch (PYSEC-2026-4140..4152,
# PYSEC-2026-4183, GHSA-pxh4-856f-4h89), two of which are fixed only in 2.15.
PyJWT==2.15.0
# python-jose removed 2026-11-19. Its one caller (api/auth/dependencies.py, the
# FastAPI bearer-token check) now uses PyJWT, like every other JWT path here.
# python-jose 3.5.0 is the latest release and still carries CVE-2026-85394 /
# PYSEC-2026-4298 (HMAC key confusion), and it pulled in ecdsa (CVE-2024-23342,
# no fix planned upstream) and pyasn1 0.4.x (eight open advisories).
bcrypt==4.0.1
# cryptography 42.0.8 (CVE fixes); pyOpenSSL bumped in lockstep because
# pyOpenSSL 23.2.0 caps cryptography at <42.
#
# cryptography 50.0.0 is the lowest release that clears every open advisory
# (PYSEC-2026-3552 is fixed only in 50.0.0). pyOpenSSL 26.4.0 is the first
# release that accepts cryptography 50 (26.3.x caps it below 50) and clears
# PYSEC-2026-2268/2269. Nothing in this service imports OpenSSL directly.
cryptography==50.0.0
pyOpenSSL==26.4.0
# authlib removed 2026-08-06. Nothing in this service imported it — one grep hit
# across the whole repository, and that hit was this line — and `pip show` in a
# fully installed environment reported no reverse dependencies. It appears to
# have come along when CE was split out of the full platform.
#
# It was not free to keep: authlib 1.3.2 carries CVE-2026-27962, an
# authentication bypass via JWK header, which Trivy reports as CRITICAL. A
# vulnerability in code nothing calls cannot be exploited, but it still fails
# the scan, and every reader has to re-derive that reasoning. Deleting it closes
# the finding outright. JWT handling here is PyJWT (see api/core/auth.py).
